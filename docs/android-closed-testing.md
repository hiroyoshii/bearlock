# クローズドテスト公開手順

2026-09-12。内部テストとクローズドテストは別トラック。既存の `Android Internal Release` workflow は内部テスト向けで、クローズドテストへはPlay Consoleから設定する。

1. Play ConsoleでBear Lockを開き、ダッシュボードのアプリ設定を完了する。ストア掲載情報、連絡先、プライバシーポリシー、広告・対象年齢・コンテンツレーティング・データセーフティ・アプリアクセス・Accessibility申告と動画など、Consoleで要求される項目を埋める。
2. 「テストとリリース → テスト → クローズドテスト」でトラックを作成／管理する。
3. 「国／地域」で配信先（日本など）を設定し保存する。
4. 「テスター」でメールリストまたはGoogleグループを設定する。Google Playにログインするアカウントを登録し、フィードバック先も設定・保存する。
5. 「リリース → 新しいリリースを作成」で、内部テストへアップロード済みのAABをライブラリから追加するか、新しい署名済みAABをアップロードする。同じversionCodeのファイルを再アップロードせず、既存ビルドを再利用する。コードを変更して再ビルドした場合は未使用のversionCodeが必要。
6. リリース名とリリースノートを入力し、確認画面のエラーを解消する。保存だけで終わらず、画面に従ってクローズドトラックへの公開操作を進め、「公開の概要」から変更を審査に送信する。
7. 審査後、管理対象の公開を有効にしている場合は「公開の概要」で承認済み変更を公開する。無効の場合は通常、承認後に自動公開される。「審査中」「公開の準備完了」とテスターに配信済みの状態を区別する。
8. テスター向け参加リンクを共有する。テスターは登録済みアカウントで参加に同意し、Google Playからインストールする。内部テスト参加者は内部テストから退出してクローズドテストへ参加する必要がある。

2023年11月13日以降に作成した個人用アカウントでは、製品版アクセスの申請前に12人以上が14日間連続でクローズドテストへオプトインする必要がある。メールリストへの登録だけでは参加にならない。CIやエミュレーターの試験はこの人数・期間要件の代わりにならない。テスターの使用状況・フィードバック・修正内容を記録する。

## Android 14の自動検証

`Android 14 Acceptance` は API 34 のエミュレーターで実行する。mainのAndroid変更時またはworkflow_dispatchで実行できる。

- 説明表示・拒否・再表示・同意後のAndroid設定への遷移
- Accessibility接続、正確なアラームの許可（CIではOS権限はADBで付与）
- 対象選択の取消／保存と履歴が増えないこと
- 予約確認の取消、確定後の履歴記録、予約編集／削除
- 本番のPlanner・GuardServiceを使った1分ロック中のProbe入力遮断と自然期限後の復帰

結果はActions artifact `bearlock-android14-acceptance` と `ci-results/android14/result.json` に保存する。実行の成否はJSONの `passed` とActionsの結論を確認する。Debug限定の1分作成補助を使用するため、Playで配布する署名済みAAB・実決済・実機/OEM省電力・Web制限・全OSの保証には広げない。
